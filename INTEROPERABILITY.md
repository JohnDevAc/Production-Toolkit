# Interoperability and setup readiness

## Lifecycle v1 — unreleased 1.4.0 candidate, 26 October 2026

Toolkit reads `toolbox-lifecycle.json` from an installed owned maintenance directory or a verified release package. It invokes native entry points with `--lifecycle-request` and PowerShell entry points with `-LifecycleRequestPath`. Paths must stay within the descriptor root; shell command strings are not accepted. Windows PowerShell uses its own system module path and a per-process execution-policy override, without changing machine policy. New complete ZIPs use the authoritative root descriptor (or one wrapper directory); independent nested product descriptors are preserved. Historical ZIP filenames do not imply protocol support: absent metadata permits an official verified legacy installer, while malformed present metadata fails closed.

Environment uses `Kiloview-Environment-Setup-Lifecycle.zip`; Job uses `NDI-Job-Configurator-Windows.zip`; Resolume uses `Resolume-Arena-Configurator-v<version>-win-x64.zip`; Agent retains its full self-contained ZIP. Job and Resolume installed maintenance descriptors support inspection/removal; repair/update require the complete verified payload. The installed Environment app is `%ProgramFiles%\Kiloview\Environment Setup\Kiloview-Environment-Setup.exe`; retained maintenance is `%ProgramData%\KiloLink\Maintenance`, with legacy Launcher fallback. Resolume maintenance is `%LOCALAPPDATA%\Resolume Arena Configurator\Maintenance`. These files survive the owner's supported app removal as documented by that owner.

Requests omit role so Environment owns its sole role choice, retain data by default and omit requestedVersion unless an expected payload version is established. A release tag is never passed as a guessed binary version. Results require schema, operation/product/action correlation, fresh timestamps and valid evidence types. Running/restart-required remain pending; terminal failed/partial/cancelled/blocked complete the attempt with its guidance. A success result emitted before parent exit retains the process lock; contradictory exit or unavailable exit evidence requires owner inspection. No process or prompt is killed. Read-only owner inspection is bounded and never becomes normal application launch. Recheck only clears an unconfirmed Toolkit lock on owner `safeToRetry:true`, no active operation and no recovery requirement; the original outcome is retained.

Explicit package install/update requests carry the verified primary payload's native version when available. Toolkit reads the uniquely identified product executable inside the verified package, or its native entry point when no product executable is present; it never borrows a companion product's version. Unknown or ambiguous payload metadata leaves the version omitted. Build metadata is excluded from the request, while prerelease identifiers are preserved. A verified saved Environment setup uses its own executable version. Installed Open setup, completion through existing installed setup and inspection/removal/repair retain their existing version-free requests.

For an explicit requested version, owner `succeeded` and `no-change` results must include installed primary-component evidence whose semantic version matches that request. Four-part Windows versions normalize trailing zeros and build metadata is ignored; prerelease differences still matter. Component matching uses the canonical product ID, not arbitrary children or channel-label spelling. A retained different version or missing evidence requires Recheck, shows the requested/reported version where known and blocks further mutation. Toolkit preserves the original owner result and never automatically retries a version switch.

Lifecycle metadata readers share deletion so polling does not block the owner's atomic result replacement. The size limit is checked against the same read-only file handle used for parsing; that handle does not share in-place writes. A transient unavailable snapshot remains unverified and is retried by normal reconciliation, never accepted as a successful result.

PC Agent **Complete setup** is distinct from package lifecycle repair. For an unconfigured installed Agent with an adjacent version-matched Setup, Toolkit opens that normal native executable with no arguments. The owner retains its licence/NIC consent and waits for its elevated UI. Toolkit records `interactive-setup` transport with an internal `install` journal action (no request is passed to the owner), tracks its process and excludes other mutations, then re-detects actual configured/running state. It never invents a lifecycle success result. Configured explicit Repair remains the advertised package-only `repair` action; no `configure` protocol action or server contract change is introduced.

Environment **Complete setup** on a partial Client, Server or combined role sends `install`, preserving data and omitting role so the owner selects it. This allows ordinary installation to skip healthy components. Explicit Repair still sends `repair`; configured updates remain `update`.

Environment **Open setup** also uses an admitted installed or retained descriptor's `install` action, with role and requested version omitted and data preserved. The owner retains its Client/Server selection and explicit consent, and can carry the same request through elevation and reboot continuation. Server setup may reconcile runtime and service components; it is not a health-only check. A legacy or unsupported installer opens normally without a fabricated owner result. Invalid maintenance metadata and known complete-package recovery requirements block this route. Reopening Toolkit retains the original operation directory; unavailable process-exit evidence still requires owner-safe inspection.

Before advertised Repair, Toolkit performs the owner's read-only inspection when supported. A validated `recoveryRequired:true` result selects a complete verified ZIP advertising `repair`; missing, incompatible, unverifiable or legacy-only packages stop before mutation without falling back to retained repair. This works with a fresh Toolkit state and persists through Recheck/restart. Compatibility uses the highest known owner component, installed executable or descriptor-resolved native repair executable version. If root executables are absent, their installed version stays unknown; retained native metadata is only a repair comparison bound. No known bound means no automatic recovery repair. Ordinary healthy/offline retained repair and retained inspect/uninstall remain available; requests still preserve data and introduce no new protocol action.

Agent runtime polling ignores maintenance-only records and rejects empty, invalid or missing executable identities without treating them as Not running. It snapshots cards, discards stale results after discovery/removal or a new action, and logs unexpected inspection failures while preserving owner recovery evidence. Missing-file rediscovery keeps the lifecycle descriptor alongside any registered uninstaller.

Portable TestCard uses Toolkit-owned receipts, a file inventory, an exclusive mutation lock and per-copy markers. Explicit inspection validates ownership and never downloads, reinstalls or starts outputs. Failed atomic activation preserves the old selection, preference loss does not orphan the installed copy, and partial removal retains ownership proof for retry. Existing saved copies are adopted only within Toolkit's exact app/package-GUID layout. Cloud placeholders require an allowed non-surrogate tag and matching final path; symlinks/junctions/unknown reparse tags fail closed.

Regression fixtures exercise protocol failures, owner handoff, close/reopen, package admission, offline readiness, portable damage/removal and WPF layout. The optional `--lifecycle-fixtures <manifest.json>` test input supplies owner fixture paths and scenarios; it retains the isolated operation evidence. Real owner fixtures are separate from Windows VM/UAC/reboot/vendor acceptance. Candidate building does not authorize publication or installation on production hardware.

## Network Job Configurator links — 7 September 2026

When local Job Configurator detection is empty, Toolkit starts independent LAN discovery during startup, explicit update checks and post-setup refresh. It verifies the current or legacy Job Configurator product on `/api/health`, then exposes each discovered TCP 8091 web UI below Install. Probes bypass internet proxies, refuse redirects, limit response size and time, cover complete supported /20–/30 subnets, and report partial/unsupported coverage. Remote discovery does not mark the application locally installed. Closing Toolkit or replacing a scan cancels pending probes; local installation clears the links. No server or companion integration contract changed.

## PC Agent setup recovery

The PC Agent card now checks per-user configuration independently of executable version. Missing, unreadable or invalid schema-1 identity/network/membership state requires **Complete setup**. It follows the agent's current/legacy state precedence and does not treat a disconnected adapter as missing setup. A matching installed Agent/Setup pair can complete configuration offline; missing or mismatched Setup requires the complete release package. Recovery retains newer installed versions. Local checks run again before actions and after setup exits, including unsuccessful or incomplete setup. Toolkit never writes Agent configuration or accepts its licence; the independently installed Setup owns those operations. The server process contract and remote consent flow are unchanged.

Validation (6 September 2026): 312 Toolkit regression/UI assertions pass, including a harmless local Setup fixture exercising incomplete exit, successful configuration, offline reuse and stale Launch recovery. The recovery card was visually checked at 100% scale and layout assertions pass at 100%, 200% and 250%. The server's 22 regression and 8 frontend checks, installer package checks and both companion validation projects also pass. All configuration fixtures use isolated paths; validation did not install software or change live NDI settings. The 1.3.3 self-contained application, ZIP and Windows installer build successfully. Publication and local installation are separate from build validation.

## Additional QA corrections — 6 September 2026

Malformed optional Agent metadata no longer discards otherwise valid Server evidence. It still prevents Client/combined deployments from reporting complete. Unsupported or unreadable component receipts produce an explicit unknown deployment status instead of being interpreted as a legacy Client installation.

## QA follow-up — 6 September 2026

Configured PC Agent evidence now requires schema 1, nonempty valid endpoint and adapter GUIDs, a usable unicast IPv4 host address and a prefix between /1 and /30. Incomplete, unsupported, link-local, loopback, multicast, network and broadcast state cannot claim a configured installation.

Live adapter/address availability is checked separately and shown in component details. A disconnected adapter does not imply missing installation components. Client-only completeness continues to require local NDI Tools and PC Agent without requiring local KiloLink, WSL or Discovery. Verified cached downloads remain installable offline; unavailable package sources block downloads before installer launch.

Toolkit launches independently released applications. It does not require local Job Configurator, KiloLink or Discovery to run on a client PC. Each component retains its own installer, repository, version and updater.

UDP to NDI and Test Card Generator use their own GitHub release feeds and settings. UDP to NDI uses its official installer. Test Card Generator is a portable package: Toolkit retains its complete folder, worker and private .NET runtime, then records the launch path without starting the generator. FFmpeg and NDI Runtime dependencies remain with the respective product; adding these cards does not change fleet, server, endpoint or NDI configuration contracts.

Environment status reads its schema-1 Client/Server role receipt plus actual local files and configuration. Client requires NDI Tools and configured PC Agent, with server components shown as not required. Combined hosts also display the Agent requirement. Server-only deployments do not require Agent. Reliable legacy client evidence can identify a client installation; shared NDI Tools alone leave the role unverified. Server removal retains shared tools without inventing a missing server deployment.

Package preparation checks the actual required release asset using the downloader's HTTPS/proxy context, handles sources that reject HEAD, and rejects captive-portal HTML. Failures prevent installer launch and explain how to retry. Bounded stalled-read timeouts, existing checksum/product checks and archive safety still apply. A complete verified cache can be used offline; cached release metadata by itself is not an installable package.

Launching installed apps and local self-contained installers does not need internet. Environment and PC Agent Setup perform authoritative checks for their own secondary downloads, including when launched outside Toolkit. These checks can use a separate internet adapter from the production LAN.

Job Configurator and Environment Server require their intended signed-in administrator account; their per-user/WSL startup cannot safely be assigned to a standard-user desktop by entering another account at UAC. Client PCs normally use the remote services and do not need those server components installed.

Validation: `dotnet run --project tests/ToolkitLauncher.Tests/ToolkitLauncher.Tests.csproj`. Full installer/elevation/reboot behavior remains part of controlled deployment acceptance.
