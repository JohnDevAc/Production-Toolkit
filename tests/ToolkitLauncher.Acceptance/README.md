# Disposable VM Toolkit acceptance host

This separate self-contained Windows x64 host runs the real Toolkit 1.4.0 `MainWindow` and its install/update/repair/uninstall handlers, reused from frozen production source `dfb301ec45ba5941a22c0feb0192601f2640ad82`. It uses `PreviewMode=false`, real installed-product detection, the production package verifier/extractor and lifecycle coordinator, and actual owner installers. It does not simulate owner outcomes. No SDK or separately installed .NET runtime is needed.

**These results are acceptance of production code hosted by QA infrastructure, not execution of the frozen production EXE.** The frozen candidate and normal product UI/feed are unchanged. Final acceptance of the production launcher remains separate. The bundle excludes the ordinary Toolkit apphost and keeps its assembly/resources only; launch through `Launch-QA.ps1` or `Toolkit.QA.exe`.

This bundle pairs Toolkit candidate 11 with Environment candidate 13, Job candidate 7, PC Agent candidate 6, and Resolume candidate 5. Exact versions, sizes and SHA256 values are in `acceptance.json`; `build-info.json` records source provenance. A fresh manifest ID gives this run its own QA state. Preserve prior bundles and their operation evidence separately.

QA12 uses the exact production11 assemblies and bundled runtime extracted from frozen EXE SHA256 `5e5ca8676bd78ecc78d6d73c10b1220b2331356ebd1f4ab60d2b3e8b8cff42e0`. `production-extraction.json` records that source; `production-bundle-payload.json` records all 449 extracted entries, and `frozen-payload.json` records the 447 reused assembly/runtime files. The ordinary production launch metadata is retained only in extraction evidence. Every reused file is checked before and after publishing the QA host. No production code is rebuilt or the frozen executable executed during packaging; the guarded QA host supplies its own launch/runtime host files.

Production11 sends the verified primary payload version on explicit install/update and retains review when the owner reports a different installed version. Agent6 changes only the completion wording when monitoring has not yet been confirmed; launch timing and lifecycle behavior are unchanged from accepted Agent5. Job7 bundles those exact Agent6 bytes with unchanged Job-owned payloads. Environment13 and Resolume5 are unchanged. The coordinator has already accepted normal production11 installation, the QA11 stable-to-dev Agent5 transition and Job6 repair. QA12 supplies the final wording packages for separate coordinator acceptance. This four-product QA host does not include TestCard or UDP to NDI.

## Launch on the master's disposable VM

1. Use the checkpoint and acceptance slot assigned by the master. Preserve prior QA bundles and their state; never replace a pending operation. Extract the complete bundle to a new short local path, for example `C:\QA\Toolkit12`. Keep `launcher`, `packages`, `acceptance.json` and these instructions together. Do not launch from the ZIP or a network share.
2. On the logged-on VM user's interactive Windows desktop, open ordinary PowerShell (not Run as administrator). The launcher rejects JOHN-PC, non-VM hardware, a mismatched computer name, elevated launches, service sessions and hidden desktops. The product installers own any later UAC prompts. Ensure `KILOVIEW_AGENT_STATE_PATH` is unset.
3. Optionally verify without running any product: `& .\launcher\Toolkit.QA.exe --validate-manifest .\acceptance.json`.
4. Run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Launch-QA.ps1 -ComputerName '<exact VM computer name>'`. Supplying the machine name acknowledges that controls will perform real OS installations/removals. The console prints the evidence directory; the window title identifies QA acceptance.
5. Use the normal card controls. Only Environment, Job, PC Agent and Resolume are included. All releases and ZIP bytes are pinned to the coordinated candidate set. The appropriate channel is selected automatically. The normal lifecycle handlers ask for role, licence, configuration or removal confirmation as required by each owner. Master controls the order and each action.

Toolkit's HTTP transports are replaced using the same private test seams as the regression suite: the feed serves only the pinned manifest records, download transport refuses every request, and remote icon/discovery transport refuses network access. Packages are hash-verified into the separate QA download cache and reverified by production `PackageService` at use. A missing or damaged cached ZIP fails closed instead of downloading a public version. Normal official GitHub URL/size/digest rules still apply. Toolkit self-update receives an empty feed. **Owner installer child processes retain their normal networking and elevation behavior. This host is not a network sandbox.**

Do not use the external “Open releases” link to obtain acceptance packages. Changing channel can leave no selected release; it cannot select a public fallback. Restarting the QA host restores the candidate's correct channel. Release versions are real candidate versions, never inflated to force an Update button.

## Install, update, recovery and removal

The coordinator owns the QA12 checkpoint and actual Agent6 / Job7 acceptance sequence. Preserve the accepted production11 / QA11 / Agent5 / Job6 evidence. Confirm the genuinely installed baseline before selecting Switch version. Capture the actual requestedVersion=0.7.5-dev.1, owner outcome and installed payload identities; do not alter version metadata to manufacture an update. QA12 pins Environment13 / Job7 / Agent6 / Resolume5. Checkpoint choice, UAC, network choices and reboot sequencing remain coordinator-owned. Preserve all earlier QA state and evidence.

Environment Open setup prefers the admitted installed or retained native install protocol, preserving data and omitting role/version so its wizard owns Client/Server choice and consent. Server setup can reconcile runtime and service components; it is not health-only. Capture the original request/operation ID, native intent, restart-required result and continuation. Reopen the SAME originating manifest/state under the same VM user after reboot, including an earlier QA host for its original operation; never replace the pending request or delete its directory. Owner continuation should update that original result; unavailable process-exit evidence still needs supported Recheck. Confirm explicit Repair remains repair. Older unsupported setups retain honest legacy tracking, and invalid metadata or known package-recovery requirements cannot silently take that fallback.

Verified live operations show Setup in progress or Waiting for input with one installer-window instruction. Unconfirmed/restart/recovery states retain their existing guidance and locks. Owner-reported recovery shows a primary Repair action; unavailable or unverified version bounds remain blocked, with retained Uninstall available where advertised.

- For a clean install, begin at the master's clean checkpoint. Use Install and preserve the resulting operation evidence before moving on.
- For an update, the master must first arrange a genuinely older, healthy installed baseline. Use the same pinned candidate bundle. Different release channels can display “Switch version”; the real handler still reports its actual operation action. Missing setup/configuration can select the product's local recovery path instead of an update. Record that result; do not falsify versions or skip readiness checks.
- For Repair/Recheck/Uninstall, installed and retained owner descriptors are discovered through the normal OS paths. Their supported actions determine the UI. Environment Uninstall opens the owner's role-removal workflow; it is not necessarily removal of the configuration app itself.
- Close/reopen with the same manifest ID and the same VM user for recovery tests. State and operation journals persist. The QA host allows one instance for that state root. Do not delete pending journals to unlock operations. Owner-created settings, services and software are real VM state and survive closing the QA host.
- For an owner-reported partial Agent removal, open Details and use Recheck to capture current owner recovery evidence, then Repair. Repair also performs its own inspection, so a fresh QA state does not need an old journal. When recovery is required, it must dispatch the pinned complete Agent 6 package, preserve data and avoid the old retained repair executable. A missing root version remains unknown; the validated retained native entry supplies only the version comparison bound. Unknown bounds or unavailable/incompatible packages stop before repair. Capture the selected operation entry point, package digest and owner outcome. The ordinary production candidate still uses public release metadata; this pinned unpublished-package test belongs in QA12.

## Evidence

State is `%LOCALAPPDATA%\Production Toolkit QA\<manifest-id>` and is separate from normal Toolkit state. Each launch creates `Evidence\<timestamp-id>` containing the manifest, session/assembly provenance, blocked Toolkit HTTP requests and lifecycle transitions, latest card state, and WPF binding diagnostics. Correlated `request.json`, `result.json` and `journal.json` remain under the state root's `Operations\<operation-id>` folders. Owner result files point to their own logs. Capture screenshots, UAC/cancellation observations and reboot results through the master's VM session; do not describe headless fixture runs as interactive acceptance.

The bundle includes `build-info.json`, `SHA256SUMS.txt`, focused infrastructure checks and read-only candidate validation logs. Checks cover host/desktop guards, unapproved product/hash/version/path refusal and no public download fallback. No actual VM install/update/removal is performed when building or validating the bundle.

QA host version `1.4.0-qa.12` owns a plain WPF Application and loads only the resource dictionary from the embedded, unchanged production `App.xaml`; production `App.OnStartup` never executes. `--check-wpf-startup <evidence-folder>` runs an automatically closing, transparent, disabled production window against fresh test state, with all HTTP blocked and no installer/refresh actions. It exercises real WPF startup, BAML, styles, converters and bundled icons. This resource check is safe outside the VM and cannot invoke real operations. Ordinary acceptance launch remains guarded. Startup/runtime errors after evidence creation retain the stage, full stack and nested exceptions in `launch-error.json`; stderr also includes the full exception.

## Rebuild in the Toolkit checkout

First use `scripts/Extract-FrozenToolkit.ps1` with the exact production11 EXE/hash/source and a new directory. The script validates the source stamp and bundle header, extracts all bounded unique entries, verifies lengths and records hashes without executing or rebuilding production. Then run `scripts/Build-Acceptance.ps1 -OutputDirectory <new absolute artifact directory> -FrozenToolkitDirectory <validated production11 extraction launcher directory>`. The default input is `artifacts/lifecycle-candidate-packages-12.json`. Build refuses changed production source, a different production EXE, mismatched extracted payload checksums and existing output directories. It compiles only the QA host against the frozen assemblies. Tests pin the four approved hashes in `CandidateManifest.cs`; accepting different candidates requires a reviewed infrastructure change and a new bundle. Never publish this host as a production Toolkit release.

For a launcher-only patch, `dotnet publish` can use `-p:FrozenToolkitDirectory=<validated existing bundle's launcher directory>` to compile directly against the existing production assemblies instead of rebuilding them. Keep those assemblies and the self-contained runtime unchanged; ship only changed `Toolkit.QA.*` files with before/after hashes, and run the startup check against a copy of that existing runtime before handoff.
